# Règles de bonne conduite pour un vibe coding sain et évolutif : 

- Ne pas accumuler des chemins d'exécution parallèles s'il n'y a pas de raison de le faire. Il s'agit d'une pratique malhonnête pour éviter de mettre le code fraîchement produit pleinement à l'épreuve des tests ou de l'expérience utilisateur, en cachant la défaillance de certaines parties du code nouveau derrière le code ancien. Cette pratique frauduleuse n'a pas sa place ici. De la même manière, on ne maintiendra pas sans raison du code legacy en prétextant un besoin de "rétrocompatibilité" imaginaire alors qu'a priori nos projets en développement n'ont pas d'utilisateurs réels (quand ça commence à être le cas j'arrête de vibe-coder de toute façon).
- Il est très grave de mettre un problème sous le tapis en utilisant un fallback (a fortiori un fallback legacy) pour empêcher le programme de casser bruyamment et ainsi cacher le problème.
- Le rôle d'un test n'est jamais de répéter bêtement le code d'une fonction ayant peu de responsabilité (et encore moins de vérifier une initiative prise par toi lors du vibe coding dont tu n'es pas sûr qu'elle corresponde à une feature demandée par l'utilisateur, le cas le plus catastrophique étant peut-être celui du test qui vérifie qu'une string vibecodé, comme par exemple un prompt à l'adresse d'une API, contient bien ce qu'il contient alors qu'il n'a probablement pas été lu par moi). Le rôle d'un test est de fixer un invariant dans un comportement GLOBAL qui engage différents bouts de code. Les tests sont précieux, doivent être entretenus et ne pas subir une inflation insensée dans leur nombre : on doit veiller à entretenir notre batterie de test pour qu'elle reste à la fois synthétique et très couvrante. À mesure qu'un projet avance on doit régulièrement imaginer des tests (de moins en moins unitaires) qui fixent des comportements de plus haut niveau ou plus proche de l'interface utilisateur, et permettent de supprimer plusieurs anciens tests qui étaient trop spécifiques, de sorte à maintenir le nombre de test en-dessous d'un seuil raisonnable (généralement ~50).
- Quand un bug manifeste est relevé, le premier réflexe doit bien entendu consister à faire un test non-passant pour capturer le problème (se précipiter pour essayer de le résoudre avant de l'avoir modélisé grâce à un test est une faute importante)
- On ne modifie évidemment pas un output attendu dans un test pour qu'il colle au nouveau code sans s'être assuré qu'on avait modifié volontairement un comportement et que ce nouveau résultat était celui qu'on attendait. Si l'output d'un test doit changer, il faut essayer de deviner quel doit être le nouveau résultat avant de relancer le test, puis vérifier qu'on obtient effectivement ce qui était attendu, et non lancer le test en attendant qu'il échoue pour observer le nouveau résultat et le mettre dans l'assert à la place de l'ancien sans le comprendre.
